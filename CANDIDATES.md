**Важно, что предыдущая сессия (эта сводка) не учла:** пункт выше в этом же
файле — `render:new_render_scheduling = TRUE на этой машине` — асинхронный

новой сводки: runtime-тумблер без ребилда,
`hyprctl eval 'hl.config({ render = { new_render_scheduling = 0 } })'`,
повторить тогглы. Если блинк пропадает/меняется — это прямое попадание в
асинхронный commit-путь как источник задержки CPU-решение → скан-аут, а не
что-то специфичное для gloview. ПРОВЕРИТЬ ЭТО ПЕРВЫМ в следующей сессии —
дешевле любого code change.

**Код перепроверен (чтение исходников, без билда — нет живого Hyprland/GPU в
этой среде):**
- `open()` — одна синхронная call-stack без await/yield; `m_active=true` и
  `m_openStamp` ставятся в одной строке друг за другом. Диагностика
  `entryToActiveUs` добавлена, но по чтению кода ожидается ~0 — маловероятный
  источник многокадровой задержки.
- `hl.plugin.gloview.toggle` (addLuaFunction) вызывает `toggle()` СИНХРОННО,
  без промежуточного IPC/сокета — это НЕ то же самое, что `exec, hyprctl
  gloview` (тот путь реально форкает процесс и идёт через сокет, потенциально
  многокадровая задержка). Если бинд в конфиге пользователя использует
  `hl.bind(..., hl.plugin.gloview.toggle)` (README-паттерн), Lua-диспетчеризация
  сама по себе — не подозреваемый.
- `shouldRenderWindow` оценивается РАНО в кадре (см. комментарий у
  m_pendingDeactivate, session.cpp) — задолго до RENDER_LAST_MOMENT, где
  добавляется PainterPass. На бумаге, раз `m_active` синхронно true до начала
  render() для этого тика, окно должно скрыться с первого же кадра. Реальная
  задержка (если не render_scheduling) — с высокой вероятностью на стороне
  Hyprland: буферизация представления (double/triple buffering) между
  "CPU решил" и "GPU реально показал", то есть НЕ багом gloview как такового.

**Новая инструментация в этом коммите** (чисто диагностическая, поведение не
меняет кроме forceFullFrames 3→8, см. ниже):
- `Overview::frameTick()` — монотонный счётчик RENDER_LAST_MOMENT (публичный,
  тикает независимо от m_active) — общая система координат для всех логов.
- `TOGGLE tick=…` / `OPEN tick=… entryToActiveUs=…` — session.cpp.
- `SRW tick=… win=… class=… active=… hide=…` в hkShouldRenderWindow — только
  пока `opening()` (окно входной анимации), чтобы не заспамить лог. САМОЕ
  прямое свидетельство: покажет, действительно ли хук вызывается с
  active=true уже на первом тике после OPEN, или есть реальный гэп.
- `forceFF=` добавлено в существующий `F t=+…` трейс.
- ЭКСПЕРИМЕНТ (не подтверждённый фикс): `m_forceFullFrames` 3→8 — см. комментарий
  в session.cpp прямо на этой строке для обоснования и критерия успеха.

## Обновление 2026-09-06 (Bug A — найдена и исправлена реальная причина)

**Пункт "gloview-сторона чиста" выше — опровергнут.** Живое тестирование
(несколько раундов, реальный Hyprland/GPU) закрыло остальные версии:
`new_render_scheduling=0/1` без изменений; `SRW hide=` — скрытие окна
корректно с первого тика после `OPEN`, задержки нет; диспетчеризация бинда
синхронная (`entryToActiveUs` — единицы микросекунд); `forceFullFrames` 3 vs 8
— не влияет на блинк вообще (это защита от другого класса багов — stale
swapchain image, — оставили на 8 просто как задел, не как фикс).

**Настоящая причина** — нашлась через `grep baseDiag|backdrop e=|bdDrawn` по
тикам вокруг каждого `OPEN`, затем сверку с апстримом (fedsfarm/gloview):
`open()` (session.cpp) безусловно сбрасывал `m_backdropDrawn=false` и
`m_blur.valid=false` **на каждом** открытии, не только на первом после
загрузки плагина — подтверждено: `bdDrawn=0`/`blurOK=0` на первом кадре после
КАЖДОГО `OPEN`, идентично при повторных открытиях в одной сессии без
перезагрузки. Это форсирует полный захват wallpaper+layer-shell поверхностей
в `m_backdropSrcFB` **и** полный Gaussian-блюр в `m_blur.fb` синхронно внутри
первого отрендеренного кадра — достаточно дорогая GL-работа, чтобы иногда
промахнуться мимо vblank → чёрный блинк. Апстрим этого не имеет, потому что у
него нет своего кэша вообще — блюрит `.blur=true` каждый кадр анимации из уже
тёплого нативного кэша Hyprland (откуда и его собственная отдельная проблема:
~15x GPU в сравнении с нашим кэширующим подходом — так что откат на апстрим
НЕ вариант, он не "неэффективный", он делает принципиально другую, более
дорогую вещь каждый кадр).

**Фикс (запушен, `feat/drag-anim`):** сброс кэша теперь условный — только
если `m->m_blurFBDirty` был `true` ДО того как мы сами его перезаписываем
(`nativeBgDirty`, реальный сигнал Hyprland "фон правда поменялся"), ИЛИ кэш
старше `kBackdropCacheTTL` (3 секунды — покрывает сторонние демоны обоев,
которые не идут через Hyprland-трекинг). Таймстамп `m_lastBackdropCapture`
проставляется в `backdrop.cpp` там же, где `m_blur.valid = true`.

**Не до конца проверено:** сбрасывает ли сам Hyprland `m->m_blurFBDirty`
обратно в `false` между нашими вызовами `open()`, или держит `true` вечно
после первого нашего форса (мы этот флаг только пишем, нигде не читаем/не
ресетим сами — чисто Hyprland-internal поле, `grep m_blurFBDirty` в этом репо
даёт только наши 2 write-сайта). Если никогда не возвращается в `false` —
`nativeBgDirty` выродится в "всегда true" после первого открытия, и защита
будет работать только за счёт TTL. Это ХУЖЕ (реакция на реальную смену обоев
с задержкой до 3с вместо мгновенной), но фикс не ломает: TTL сам по себе уже
ограничивает частоту дорогого пересчёта максимум раз в 3 секунды — этого
достаточно, чтобы убрать блинк на быстрых повторных открытиях, ради которых
всё это затевалось.

**Протокол проверки для следующей сессии:** пересобрать, открыть/закрыть
overview 5-6 раз подряд БЕЗ перезагрузки плагина, визуально — блинка быть не
должно вообще ни на одном открытии (не только на первом). Параллельно
грепнуть `bdDrawn=`/`blurOK=` на первом `F t=` после каждого `OPEN` — должно
быть `1` на втором и последующих открытиях (не `0`, как было раньше), если
между открытиями прошло меньше 3 секунд. Отдельно проверить: реально сменить
обои (например через wallpaper-daemon) пока overview закрыт, открыть в
течение 3 секунд — должны увидеть на кадрах входа старые обои на долю секунды
(ожидаемый, задокументированный trade-off, не баг).

## Обновление 2026-09-06 (сессия 2: nativeBgDirty не сработал, убран)

**Живой тест первого фикса (eb81094) провалился ожидаемо предсказанным
образом.** Второй `OPEN` в логе пришёл ~1с после закрытия первого (по разнице

`m->m_blurFBDirty = true` оставлена (нужна для отдельного бага "прозрачная

**Протокол проверки:** пересобрать, открыть/закрыть несколько раз (кроме
самого первого раза после reload) — вместо чёрного (или перекрашенного)
проблеска должен сразу быть виден настоящий блюр обоев с первого кадра.
Самое первое открытие после reload может по-прежнему показать краткую
заливку `misc:background_color` — это ожидаемо и сейчас не устраняется
(кэша ещё физически нет).
